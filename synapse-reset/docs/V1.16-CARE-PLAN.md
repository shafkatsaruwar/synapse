# Synapse 1.16 — Care Roles, Care Connections & Check-In: Audit and Plan

Status: **Phase 1 (audit) complete. No feature code written yet.**
No server, account, cloud sync, or analytics is introduced by any phase below.

## 1. Audit: what exists today

**Persistence.** `lib/storage.ts` (~2,000 lines) keeps every record type in flat AsyncStorage keys (`fir_medications`, `fir_medication_logs`, `fir_appointments`, ...). There is **no profile concept**: one global set of keys. Caregiver mode is a single `fir_caregiver_profile` blob `{name, age, relation}` plus `healthProfile.userRole`, and records for the cared-for person are flagged inside the *same* global lists with `entryOwner: "self" | "care_recipient"`. Backup/import (`exportAllData`, `importAllDataTransactional`) and CloudKit backup dirty-marking hang off the same keys.

**Roles.** `UserRole = "self" | "caregiver" | "backup"` is a single exclusive value (`roleStorage`, `RoleContext`). The "Set up caregiver mode" sheet lives inline in `app/(tabs)/index.tsx` (~line 1238). Care & Sharing is `CareSharingScreen` → `SettingsScreen variant="care"`. `ManagedPersonScreen` edits the single managed person.

**Existing cloud caregiver linking** (`lib/caregiver-linking.ts`, Supabase, link codes). This conflicts with the 1.16 privacy rules. It stays dormant; the new offline flow does not reuse it.

**Notifications.** `lib/notification-manager.ts` (`NOTIFICATION_IDS`, medication categories/actions, snooze, `syncAllFromSettings`). Notification-tap routing is `NotificationNavigationTarget`. All scheduling reads the global (self) storage.

**Navigation.** `lib/navigation-registry.ts` + `screens/FeatureHubScreen.tsx` (`HEALTH_HUB` children list: ... Wellbeing, Care & Support). Check-In slots in between as a normal hub child, not a tab.

**Security.** `lib/secure-storage.ts` and `lib/encryption.ts` are explicitly **not** real encryption (their own headers say so). Health data is plain AsyncStorage. `expo-local-authentication` is present (biometric gate). **Not installed:** expo-secure-store, expo-camera, expo-file-system, expo-sms, a QR generator, any signature/AEAD library. `expo-crypto` gives digests and random bytes only.

**Time zones.** No IANA handling anywhere; `Intl.DateTimeFormat` is used for display only.

## 2. Conflicts and proposed compliant alternatives

1. **Profile isolation vs. flat storage.** True isolation is impossible with global keys and an `entryOwner` flag. *Plan:* keep the Self profile on the **legacy keys untouched** (zero migration risk for existing users) and namespace every other profile as `fir_p_<profileId>_<key>`. `storage.ts` gets one key resolver plus an explicit `profileId` argument; background paths (notifications, widget, badge, backup) are pinned to Self. Existing `entryOwner: "care_recipient"` records and the old `fir_caregiver_profile` are migrated **copy-first** into a new caregiver-managed profile, with the originals kept until the user confirms.
2. **"Authenticated encrypted exchange" needs primitives we don't have.** Plan: add `@noble/curves` (Ed25519/X25519) and `@noble/ciphers` (XChaCha20-Poly1305): audited, pure JS, no network, no custom crypto. Private keys go in the iOS Keychain via `expo-secure-store` (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`). If any piece cannot be completed reliably, the UI says "Not verified" and never shows a trusted connection.
3. **Native additions force a native build.** `expo-secure-store`, `expo-camera` (QR scan + `NSCameraUsageDescription`), `expo-sms` (Messages composer), `expo-file-system` (invitation/package files), plus a pure-JS QR generator. The `ios/` folder is committed, so these need `pod install` on the EAS builder and a manual Info.plist string. That is all part of the single 1.16 build.
4. **Version.** The spec says "1.16, Build 1". The repo is currently **1.16.1 (build 1)** because Apple closed the 1.15 train and you asked for 1.16.1. Also, 1.15 build 27 was already uploaded, so the "no iterative builds" rule applies from here on. Decision needed (see questions).
5. **Delivery claims.** Messages/phone/share sheet are launched by the user; Synapse never records "sent/delivered/read", only "message prepared".
6. **Revocation, guardianship, offline.** Documented in-app: revocation stops new exports only; guardian status is never "verified" offline.
7. **Two physical iPhones.** Not available in this environment. Everything that needs two devices is implemented and unit-tested at the logic level, and listed as "unverified on device" in the release notes.

## 3. Data model (all local, all versioned)

`LocalCareProfile { id, schemaVersion, type: self|caregiver_managed|connected_reference, displayName, dob?, ageLegacy?, relationship?, timeZone (IANA), medScheduleTimeZone, contactHours, createdAt, updatedAt }`
`CareRelationship { id, profileId, kind: caregiver_for|backup_for|cared_for_by, guardianClaim: none|self_declared }`
`CareConnection { id, profileId, peerName, peerPublicKey, ownKeyId, state: invitation_created|awaiting_confirmation|connected_locally|needs_verification|revoked|removed, grants: SharingPermission[], lastImportAt }`
`SharingPermission { category: med_schedule|upcoming_appointments|med_confirmations|selected_records|emergency_info, access: view (default) }`
`ConnectionInvitation { v, nonce, expiresAt, inviterPublicKey, displayName, relationship, signature }`
`SharedDataPackage { v, connectionId, recipientKeyId, exportedAt, payload (AEAD), signature }`; imported records carry `{source, eventAt, exportedAt, importedAt, isSharedCopy}`.
`CheckInReminder`, `CheckInEvent` (prepared/opened/dismissed/completed only), `ContactPreferences` (quiet hours, delay 10/15/30/custom, frequency, contact windows).

## 4. Phases

0. **Housekeeping (this plan).**
1. **Data architecture.** Profile registry, key resolver, migration with copy-first and rollback, active-profile context, "viewing X" banner, tests for isolation.
2. **Care roles and caregiver mode.** Non-exclusive roles, extended setup sheet (DOB-preferred, legacy age kept), "How would you like to manage their care?" (On This iPhone / Connect With Their Synapse), People I Care For, profile switching, caregiver-vs-recipient confirmation source on med logs.
3. **Care Connections.** Key generation, signed invitations, QR + share-sheet flows, mutual confirmation (short verification code compared out loud), permissions UI, encrypted export/import with preview, dedupe, replay/tamper rejection, honest revoke.
4. **Check-In.** New Health card (between Wellbeing and Care & Support), My Check-Ins / People / Reminders, send and check-on-someone templates, Messages / call / share sheet, history with delete.
5. **Smart reminders.** IANA zone math with DST gap/overlap handling, delay, quiet hours (spanning midnight), contact windows, postponement explanations, wording rules (never "missed"). Pure-function core, tested in Node for Boston/London/LA/Dhaka and DST boundaries.
6. **Integration** with profiles/connections; **QA** (isolation, migration, security, a11y, dark mode); **release prep** of the single 1.16 build, with no upload without your approval.

## 5. Release rule

No EAS build, submit, App Store Connect upload, or TestFlight release is started without explicit approval.
