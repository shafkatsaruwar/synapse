# Medication Enforcer audit and implementation plan

## Audit (2026-11-03)

- **Runtime and navigation:** The active product is `synapse-reset`, using Expo SDK 54 (`expo ~54.0.27`), React Native 0.81.5, Expo Router 6, and the existing theme/context system. The product UI is primarily composed from `screens/MedicationsScreen.tsx`; there is no separate public medication-enforcer route or tab.
- **Medication source of truth:** Medication records, doses, recurrence fields, and medication logs are defined and normalized in `lib/storage.ts` and accessed by `lib/storage-self.ts`. The active app is local-first and uses AsyncStorage; Supabase is an optional authentication/cloud integration, not the current medication store.
- **Schedules and reminders:** `lib/notification-manager.ts` schedules the existing medication reminders and handles notification actions. `lib/medication-schedule.ts` and the medication screen contain recurrence/time handling. The existing reminder engine supports more cadence values than the enforcement prototype currently consumes.
- **Existing prototype:** `lib/med-enforcement-core.ts`, `lib/med-enforcement.ts`, `constants/med-enforcement-copy.ts`, `MedicationEnforcementCard.tsx`, and notification-manager hooks already implement a disabled local prototype with idempotent Taken writes, snoozing, bounded scheduling, and pure tests. It currently uses a global local setting, not per-medication configuration or secure entitlement.
- **Authentication and privacy:** `contexts/AuthContext.tsx` exposes the Supabase session/user, and the implementation now fails closed unless the authenticated provider is Apple and the UUID is server-allowlisted. Medication and enforcement records remain local-first; the added Supabase migration provides the owner-only entitlement/config/event tables and RLS needed for the cloud authorization boundary. AsyncStorage is not an encrypted store, so encrypted offline persistence remains required before claiming full privacy compliance.
- **Data and lifecycle gaps:** Existing medication edits/deletes do not yet maintain a separate per-medication enforcement configuration or a dose-event audit trail. The prototype only generates daily candidates, excludes weekly/interval schedules, and does not safely model explicitly scheduled PRN occurrences. It finalizes unanswered prior dates as `MISSED`, which conflicts with the requested distinction between unresolved and confirmed not-taken.
- **UX and safety gaps:** The prototype is mounted as a compact card rather than owner-only medication-detail/settings/history surfaces. It lacks Taken-earlier, clinician-deferred, Need guidance, bounded configurable snooze controls, lock-screen privacy configuration, clinician-approved sick-day-plan linking, and the requested neutral four-message copy. Existing emergency/sick-mode access must remain independent.
- **Compatibility:** Existing medication logs remain the canonical adherence source and the prototype correctly avoids changing them except for an explicit Taken action. Existing notification reconciliation runs from settings synchronization, but app foreground/sign-in/logout and schedule-edit reconciliation need explicit enforcement hooks.

## Implementation plan

1. **Foundation and authorization:** Add a safe Supabase migration for owner-only entitlement/config/event tables with RLS, default-deny policies, unique dose-instance constraints, and no public owner identifier. Add a server-validated entitlement client with fail-closed behavior. Keep a secure local-only fallback explicitly limited to installations with no authenticated cloud capability; never describe client hiding as backend security.
2. **Domain model and persistence:** Introduce per-medication enforcement configuration and separate dose-event/event-history records keyed by existing medication IDs. Preserve existing medication/log schemas and data. Add encrypted local persistence for offline owner data, an outbox/reconciliation path, logout/account-switch cleanup, and deletion of enforcement history without deleting medications.
3. **Occurrence and state engine:** Replace the prototype’s daily-only candidate generation with schedule-derived daily, multiple-dose, weekly, interval/custom, and explicitly scheduled PRN occurrences. Use the medication’s existing local-time schedule, DST/time-zone-safe occurrence conversion, deterministic IDs, duplicate constraints, and the requested unresolved/resolved state distinctions.
4. **Notifications:** Integrate the existing Expo Notifications manager without duplicating ordinary medication reminders. Use deterministic per-dose identifiers, default offsets T0/+5/+10/+15, privacy-safe content by default, bounded horizon replenishment, permission handling, reconciliation on launch/foreground/edit/sign-in, and cancellation on resolution, disable, medication archive/delete, entitlement revocation, or logout.
5. **Owner-only UI:** Add an authorized-only Medication Enforcer settings section, medication detail switch/settings link, and optional private dashboard/history. Follow existing themes/accessibility patterns. Add Taken now/earlier, Not taken with optional reason, capped Remind later, Need guidance using only stored clinician-approved instructions, and a visible emergency/sick-day-plan link where available.
6. **Tests and rollout:** Add pure tests for authorization gates, all recurrence/time-zone cases, state transitions, notification IDs/cancellation/duplicates, offline reconciliation, account changes, permission denial, and compatibility with existing reminders. Validate native notification actions in an EAS development build/TestFlight. Keep the compile-time flag and per-account entitlement disabled until the owner reviews the migration, RLS, privacy, and device behavior.

## Required configuration before enabling

- Supabase project migration execution and review of RLS policies.
- Secure server-side owner entitlement binding/configuration; no client email or hardcoded UUID.
- EAS development build/TestFlight testing for notification actions and lock-screen privacy.
- Product decision on the approved local encrypted-storage implementation for offline mode and the retention period for enforcement event history.
